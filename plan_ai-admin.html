Лимиты Hobby — хватит x100
Факт 30д (скрин Usage): Function Storage 241MB/10GB (2%), Deployment Storage 65MB/10GB, Edge Requests 401/10M (0.004%), Invocations 17/1M, Fast Data Transfer 7MB/100GB, CPU 1с/4ч. Второй проект льётся в тот же аккаунт, но потолок общий — всё равно запас огромный.

Прогноз: 3 пилота × 20 диалогов/день × 30 дней = ~1800 invocations/мес + столько же edge. 30 ботов × 50 диалогов = ~45к invocations/мес = 4.5% лимита 1M. Bandwidth: 1 webhook ~3-5KB → 45к × 5KB = 225MB/100GB = 0.2%. Упремся только на ~500+ активных ботов — тогда Pro $20.
Хостинг кабинета — что где лежит
1) Vercel serverless app/api/* (Next.js App Router) — webhook + cabinet CRUD, free, timeout Hobby ~10с.
2) Supabase free — отдельный проект (не смешивать с лендингом), 500MB база, таблицы cabinets/bots/dialogs/messages/usage_daily. Пилот: запросы через service_role только server-side + explicit where cabinet_id, RLS — следующим шагом (JWT с cabinet_id в claims).
3) Telegram Bot API — free, long-poll нет, только webhook /api/webhook/[botId] + secret_token.
4) LLM: DeepSeek deepseek-flash V4.1 primary (off-peak $0.15/1M miss, $0.003/1M кэш-hit, $0.6/1M out) + Groq free fallback. system_prompt первым байт-в-байт — кэш держится со 2-го сообщения. Токены ботов — AES-256-GCM в ENC_KEY, в базе только iv:tag:cipher hex.
Правила и риски — решение: async webhook
— Hobby формально non-commercial в ToS: 3 free-клиента ок, платящие 12к/мес → Pro $20/мес, заложить после Дня 1.
— Решение зафиксировано: webhook отвечает Telegram 200 OK сразу (<1с), LLM крутится уже после ответа. Ответ клиенту — отдельным вызовом sendMessage, не в теле webhook-ответа. Тогда бюджет LLM (DeepSeek 4с → retry → Groq) не давит на 5-секундный ретрай Telegram вообще.
— Cold start Vercel ~0.5-1.5с — входит в <1с? Нет — поэтому 200 отдаём до тяжёлой работы (сначала 200, потом Supabase+LLM).
— Секреты только в Vercel Env, никогда в гит. .env в .gitignore.
Расчёт нагрузки (прикидка на салфетке, точное — по usage_daily после пилота): 1 сообщение клиента = 1 invocation webhook. Средний диалог 6 сообщений = 6 вызовов LLM (~2к токенов каждый = ~12к токенов/диалог). Пилот 3 салона × 20 диалогов/день × 30 дней = 1800 диалогов = ~21.6M токенов ≈ ~$5.8/мес. Важно: $48 за 15к диалогов — это совокупный расход десятков ботов (~25 ботов × 600 диалогов ≈ $48 против ~$650 дохода 25 × $25), а не расход одного клиента. Один салон физически не даст 15к диалогов/мес (~500/день). Экономика работает уже на пилоте ($2-6 против $75), не «после масштаба». Кэш системного промпта + короткие ответы + кап по usage_daily. Не считать сметой.

Supabase schema.sql: cabinets(id, owner_tg_id unique, owner_tg_username) → bots(id, cabinet_id, bot_token_enc iv:tag:cipher, bot_username, business_name, system_prompt [кэш-префикс], status active|paused|trial, trial_ends_at, token_limit_daily 50000) → dialogs(id, bot_id, client_tg_id, status ai|human|closed, last_msg_at, unique(bot_id,client_tg_id)) → messages(id, dialog_id, role user|assistant|system_handoff, content) → usage_daily(bot_id, day PK, tokens_in, tokens_out, msg_count). Индексы: bots(cabinet_id), dialogs(bot_id), messages(dialog_id,created_at). RLS осознанно позже: пилот = service_role server-side + where cabinet_id, без кастомного JWT-мостика TG→Supabase Auth.

Webhook flow — async waitUntil (решение зафиксировано): клиент → Telegram POST /api/webhook/[botId] → проверка X-Telegram-Bot-Api-Secret-Token (= secret_token из setWebhook, 401 при чужом) → сразу 200 OK → waitUntil(processUpdate): getBot → decrypt(bot_token_enc) → история → askBot(system_prompt, history, text) → sendMessage(token) отдельным вызовом → запись messages + usage_daily → checkHandoffConditions. Владелец → кабинет App Router → /api/cabinet/* → Supabase (боты, диалоги, toggle AI/человек, расход).

Handoff: «позови человека» (фразы + LLM-детект) / >2 уточнений подряд / 10 мин тишины → status=human + sendMessage владельцу (решить: тот же бот или отдельный уведомительный). Таймаут 10 мин — НЕ Vercel Cron (Hobby: макс раз в сутки, чаще — реджект деплоя): GitHub Actions schedule */5 * * * * → /api/cron/check-handoff + ленивая проверка при новом сообщении.

Архитектура целиком:
Клиент бизнеса → Telegram → POST /api/webhook/[botId]
1. Проверка secret-заголовка
2. Быстрый ответ 200 OK
3. waitUntil(): фоновая обработка
→ Supabase: найти bot по botId, расшифровать токен, взять историю
→ lib/llm.ts: DeepSeek primary → timeout 4с → Groq fallback
→ Telegram sendMessage (отдельный вызов, не через return вебхука)
→ Запись в dialogs + usage_daily
→ Handoff: если да, статус=human + уведомление владельцу в личку
Владелец → Next.js кабинет (App Router) → /api/cabinet/* → Supabase (боты, диалоги, toggle AI/человек, расход).
Ключевое: вебхук НЕ ждёт LLM чтобы ответить Telegram. Ответ клиенту — отдельным HTTP к Telegram API из фона. Убирает таймаут и ретраи апдейтов.

Схема БД (Supabase, Postgres — дословно):

create table cabinets (
  id uuid primary key default gen_random_uuid(),
  owner_tg_id bigint unique not null,
  owner_tg_username text,
  created_at timestamptz default now()
);

create table bots (
  id uuid primary key default gen_random_uuid(),
  cabinet_id uuid references cabinets(id) not null,
  bot_token_enc text not null,      -- iv:authTag:ciphertext, hex
  bot_username text,
  business_name text,
  system_prompt text not null,      -- прайс/описание — стабильный префикс для кэша LLM
  status text default 'active',     -- active | paused | trial
  trial_ends_at timestamptz,
  token_limit_daily int default 50000,
  created_at timestamptz default now()
);

create table dialogs (
  id uuid primary key default gen_random_uuid(),
  bot_id uuid references bots(id) not null,
  client_tg_id bigint not null,
  status text default 'ai',         -- ai | human | closed
  last_msg_at timestamptz default now(),
  created_at timestamptz default now(),
  unique(bot_id, client_tg_id)
);

create table messages (
  id uuid primary key default gen_random_uuid(),
  dialog_id uuid references dialogs(id) not null,
  role text not null,               -- user | assistant | system_handoff
  content text not null,
  created_at timestamptz default now()
);

create table usage_daily (
  bot_id uuid references bots(id) not null,
  day date not null,
  tokens_in bigint default 0,
  tokens_out bigint default 0,
  msg_count int default 0,
  primary key (bot_id, day)
);

create index on bots(cabinet_id);
create index on dialogs(bot_id);
create index on dialogs(bot_id, client_tg_id);
create index on messages(dialog_id, created_at);
create index on usage_daily(bot_id, day);

create table bookings (
  id uuid primary key default gen_random_uuid(),
  bot_id uuid references bots(id) not null,
  dialog_id uuid references dialogs(id) not null,
  client_name text,
  client_contact text,
  service text,
  requested_time text,              -- как сказал клиент, текстом
  status text default 'pending',    -- pending | confirmed | rejected
  created_at timestamptz default now()
);
create index on bookings(bot_id, status);
create unique index bookings_one_pending_per_dialog on bookings(dialog_id) where status='pending';

create table processed_updates (
  update_id bigint primary key,     -- анти-дубль ретраев Telegram
  bot_id uuid references bots(id) not null,
  created_at timestamptz default now()
);
Про RLS — сознательное решение: на пилоте (3 бота, 1 таблица владельцев) все запросы идут через serverless-функции с service_role ключом, который никогда не попадает на клиент. Изоляция между владельцами обеспечивается explicit where cabinet_id = $1 в каждом запросе кода, а не политиками БД. Это не "менее безопасно" при условии, что service_role ключ действительно нигде не светится — но это временное упрощение, чтобы не городить кастомный JWT-мостик между Telegram Login и Supabase Auth прямо сейчас. RLS + JWT с cabinet_id в claims — следующий шаг, когда появится больше одного человека, работающего с базой (то есть когда это станет реально важно).

Шифрование токенов ботов (AES-256-GCM — дословно):

import crypto from 'crypto';

const ALGO = 'aes-256-gcm';
const KEY = Buffer.from(process.env.ENC_KEY!, 'hex'); // 32 байта, сгенерировать: openssl rand -hex 32

export function encrypt(text: string): string {
  const iv = crypto.randomBytes(12);
  const cipher = crypto.createCipheriv(ALGO, KEY, iv);
  const enc = Buffer.concat([cipher.update(text, 'utf8'), cipher.final()]);
  const tag = cipher.getAuthTag();
  return `${iv.toString('hex')}:${tag.toString('hex')}:${enc.toString('hex')}`;
}

export function decrypt(payload: string): string {
  const [ivHex, tagHex, dataHex] = payload.split(':');
  const decipher = crypto.createDecipheriv(ALGO, KEY, Buffer.from(ivHex, 'hex'));
  decipher.setAuthTag(Buffer.from(tagHex, 'hex'));
  return Buffer.concat([decipher.update(Buffer.from(dataHex, 'hex')), decipher.final()]).toString('utf8');
}

// app/api/webhook/[botId]/route.ts
import { waitUntil } from '@vercel/functions';

export async function POST(req: Request, { params }: { params: { botId: string } }) {
  const secret = req.headers.get('x-telegram-bot-api-secret-token');
  if (secret !== process.env.TELEGRAM_WEBHOOK_SECRET) {
    return new Response('unauthorized', { status: 401 });
  }

  const update = await req.json();

  waitUntil(processUpdate(params.botId, update)); // не await — вебхук уже отвечает

  return new Response('OK', { status: 200 }); // отвечаем Telegram мгновенно
}

async function processUpdate(botId: string, update: any) {
  if (update.callback_query) return handleCallback(botId, update.callback_query); // кнопки Confirm/Reject
  const bot = await getBotFromSupabase(botId);
  if (bot.status !== 'active') return; // paused|trial-ended: глушим без LLM
  if (await alreadyProcessed(update.update_id)) return; // анти-дубль ретраев
  const token = decrypt(bot.bot_token_enc);
  const history = await getRecentMessages(update.message.chat.id);

  const reply = await askBot(bot.system_prompt, history, update.message.text);

  await sendTelegramMessage(token, update.message.chat.id, reply.text);
  await saveMessageAndUsage(botId, update, reply);
  await markProcessed(update.update_id, botId);
  await checkHandoffConditions(botId, update, reply);
}

Актуальные цены DeepSeek на сентябрь 2026 (модель deepseek-flash, V4.1): off-peak $0.15/1M входных токенов при промахе кэша, $0.003/1M при попадании в кэш, $0.6/1M выходных. Кэш держится автоматически на неизменном префиксе промпта — то есть system_prompt (описание бизнеса + прайс) должен идти первым и оставаться байт-в-байт одинаковым между вызовами одного бота, а история диалога и новое сообщение — после него. 1) curl -X POST .../api/webhook/test-bot -H "x-telegram-bot-api-secret-token: wrong" → должен быть 401.
2) Round-trip шифрования: encrypt(token) → decrypt() → совпадает с оригиналом.
3) Симулировать падение DeepSeek (неверный ключ) → убедиться что Groq подхватывает автоматически.

5) Проверить handoff-таймаут вручную — написать боту, не отвечать 10 минут, убедиться что статус переключился и пришло уведомление.
